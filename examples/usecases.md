# 想定ユースケース
ツールの単体使用に加え、以下のような複数ツールの利用を想定する。

## ユーザーの作成

- プロンプト: 
  - xxxさんをOCIに追加してください
- 想定される実行: 
  - ユーザー「xxx」をHRデータベースから検索。姓名やメールアドレスを取得し、OCIユーザーを作成する


## ユーザーの権限調査

- プロンプト: 
  - YYYさんは何の操作が許可されていますか
- 想定される実行: 
  - YYYさんユーザーを特定。必要に応じてHRデータベースへの検索を行う。その後、該当ユーザーが所属するグループすべてと、それに関連するポリシーを参照し、最終的にそのユーザーが許可されている操作を返却する

なお、これはアクセスエラーの自動デバッグ（トラブルシューティング）も含みます
対象ユーザーの所属グループ、割り当てられているポリシー群、およびネットワークソース制限（IP制限）などを横断的に評価し、「Allow group 'domain_name'/'Dev_group' to manage autonomous-databases のポリシーが欠落しているためアクセスが拒否されています」といった明確な原因と、解決のための修正案（ポリシー文）を提示します。

例） 「〇〇さんが『開発環境のAutonomous Databaseにアクセスできない』と報告してきました。原因を調べてください。」

## ポリシーの影響度調査
- プロンプト: 
  - ZZZポリシーを削除するとどのような影響があるか
- 想定される実行: 
  - 該当するポリシーを特定し、その中に設定されているステートメントを参照。削除したときの影響度を推測したうえ、影響のあるサブジェクト（グループおよびユーザー）の特定までを行う。


## OCI資格情報確認

- プロンプト: 
  - OCI資格情報を所持しているユーザーをリストアップして
- 想定される実行: 
  - OCI資格情報（APIキー・認証トークン）を所持しているユーザーを整理する。そのユーザーが最近30日間ログインしていない場合、は指摘する


## コンパートメント階層の確認

- プロンプト:
  - devday26 のコンパートメント階層を表示して
  - inactive も含めてコンパートメント一覧をJSONで表示して
- 想定される実行:
  - `list_compartments` を実行し、devday26 を起点に階層を再帰取得する
  - デフォルトでは inactive/deleted を除外し、指定時のみ含める
  - name / compartment OCID / parent compartment OCID / lifecycle を返す


## コンパートメント内リソース一覧の確認

- プロンプト:
  - devday26 のリソース一覧を表示して
  - devday26 配下も含めてリソース一覧を出して
- 想定される実行:
  - `list_resources` を実行し、指定コンパートメント内のリソースを一覧化する
  - 可能な限り Resource Search を優先利用する
  - 権限不足で一部取得できない場合は、取得済み範囲と未取得範囲を分けて返す
